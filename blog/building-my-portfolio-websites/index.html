Two Websites, One System: How I Architected My Portfolio Without Letting AI Run the Project

14 Nov 2026

There is a version of this project where I open ChatGPT or GitHub Copilot, type “build me a portfolio website,” and publish whatever comes back. The result might even look polished.

That is not how I approached it.

Generating a website is one thing. Understanding its architecture, maintaining its code and managing future changes is another.

I wanted to treat my websites as software projects, not one-off design exercises. That meant defining requirements, making architectural decisions, organizing content and using AI to support implementation rather than letting it make those decisions for me.

The Premise: One Identity, Two Websites

I started with two different goals.

The first was a professional website to present my experience, selected case studies and technical writing.

The second was a personal space for travel stories, cultural experiences and life beyond work.

Combining everything into one website would have been possible, but the content had different purposes and needed different presentation styles.

Instead, I built two independent Hugo websites connected through a shared domain:

  • Professional: amrutha.org
  • Beyond Work: amrutha.org/beyond-work/

Both maintain their own source code, content and deployment workflows while sharing a consistent visual identity.

The separation allows each website to evolve without requiring changes to the other project’s templates or content structure.

Data Modeling Came Before Templates

One of the most important decisions was how to organize information before building the interfaces around it.

For the professional portfolio, I developed a three-tier presentation structure that distinguishes selected case studies from other project experience.

Project metadata is maintained in structured data files, including JSON, while reusable Hugo templates control how that information appears.

This separation makes it easier to update titles, descriptions and project information without repeatedly editing HTML.

The same principle applies to the Blog. Articles live in Markdown files with front matter defining their titles, descriptions, publication dates and draft status.

Hugo uses that information to generate individual article pages, calculate reading time and organize the listing chronologically.

Once the templates exist, adding an article becomes primarily a content task.

Using AI Without Delegating the Decisions

ChatGPT and GitHub Copilot were part of my development workflow, alongside VS Code.

But I did not use a one-click AI website builder.

I worked incrementally: defining what a component needed to do, reviewing implementation suggestions, integrating changes into the existing codebase and checking the results locally.

Three practices shaped how I used AI:

  • Define the requirements first. Specify the component’s behavior, constraints and relationship to existing templates before requesting implementation.
  • Review the suggested code. Check whether the implementation fits the Hugo architecture rather than introducing unnecessary duplication or complexity.
  • Validate the result. Build the website and inspect its behavior instead of assuming generated code works correctly.

AI helped accelerate implementation and exploration. Architectural choices, design decisions and release readiness remained my responsibility.

This distinction matters because a successful code generation step is not the same as a reliable, maintainable feature.

A Text-First Approach to Technical Writing

I deliberately gave the two websites different editorial approaches.

The professional Blog focuses on readable typography, article titles, descriptions, publication dates and structured content. There are no mandatory featured images.

For technical articles, code blocks and comparison tables can add more value than decorative visuals.

Beyond Work is more visually oriented. Photography and storytelling have a natural place in articles about travel and personal experiences.

Rather than forcing both websites into an identical design, I kept the visual identity connected while allowing the content to determine its presentation.

The Architecture and Technology Stack

I chose a lightweight static architecture instead of a database-backed content management system or a large front-end framework.

The main technologies are:

  • Hugo: Static site generation with Markdown, structured data and reusable templates.
  • HTML, CSS and JavaScript: Custom layouts, responsive styling and interactive portfolio components without relying on a large UI framework.
  • TOML and JSON: Website configuration, article metadata and structured portfolio content.
  • VS Code: Editing, navigating and maintaining the codebase.
  • Ubuntu: Running Hugo for local development and website builds.
  • Git and GitHub: Version control, private source repositories and public deployment repositories.
  • GitHub Actions: Building and publishing the generated websites.

The goal was to keep the implementation understandable and avoid adding infrastructure that the websites did not need.

Keeping Development Private and the Websites Public

The final deployment architecture introduced another important decision: separating development repositories from published website files.

Each website has two GitHub repositories.

This setup lets me maintain the source projects privately while publishing the generated HTML, CSS, JavaScript and other website assets through GitHub Pages.

The private repositories retain the development history and reusable Hugo source templates. The public repositories contain the files needed to serve the websites.

Public website assets remain inspectable, as they are on any publicly accessible website, but the complete development repositories are not exposed.

Deployment with GitHub Actions

Both websites use GitHub Actions workflows running on Ubuntu.

The deployment process follows the same pattern:

  1. Retrieve the Hugo source from the private repository.
  2. Build the production website using Hugo.
  3. Exclude unpublished draft content.
  4. Copy the generated files into the corresponding public deployment repository.
  5. Publish the website through GitHub Pages.

Deployments are currently triggered manually, allowing changes to be reviewed before publishing.

The professional website is served at the root of amrutha.org, while Beyond Work is published as a separate GitHub Pages project under /beyond-work/.

This arrangement keeps both websites independently deployable while presenting them under one domain.

Preparing for Release

A successful local build is only one part of releasing a website.

My release process includes checking navigation, responsive layouts, internal links, article publication settings and the generated output.

The deployment setup also required configuring the custom domain, DNS records and HTTPS.

Both websites are now accessible through their intended public URLs.

There are still improvements to make, particularly around contact options, legal-page review and ongoing accessibility checks. I see those as part of maintaining the websites rather than treating launch as the end of the project.

What I Learned

Building these websites reinforced several practical lessons.

A clear content model reduces repeated work. Reusable templates and structured data make future updates easier to manage.

AI assistance still requires technical judgment. Generated code needs review, integration and testing.

Privacy can influence architecture. Separating source repositories from deployment repositories provides more control over what is publicly exposed.

A release workflow should be intentional. Keeping development and publication separate makes it easier to review changes before they become public.

The most useful outcome was not simply having two websites online.

It was building a foundation that I understand, can maintain and can extend without starting over each time.

Good architecture should make the next change easier, not just the first release faster.
