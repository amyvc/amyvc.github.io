Two Websites, One System: How I Architected My Portfolio Without Letting AI Run the Project

14 Nov 2026

There is a version of this project where I open ChatGPT or GitHub Copilot, paste in “build me a portfolio website,” and publish whatever comes back. The output usually looks fine. Sometimes it even looks polished.

That is not how I approached it.

When you let AI generate an entire site unchecked, you end up with brittle markup, duplicated styles and code you cannot easily maintain six months later. Treating a personal website like a real product meant starting with clear requirements, designing a clean architecture first and using AI as an implementation accelerator rather than the decision-maker.

The Premise: One Identity, Two Websites

I began with two distinct goals that did not belong in the same container. I needed a professional space to present my delivery experience, case studies and technical writing—and a personal space. So, I designed them as two independent Hugo projects backed by separate GitHub repositories under a shared domain.

Each site shares a cohesive visual identity while keeping its codebase, content model and release cycle completely independent.

Data Modeling Came Before Templates

The hardest part of the build was not writing HTML or CSS—it was deciding how information should be structured so the site could grow without layout rewrites.

On the portfolio page, for example, I designed a three-tier hierarchy. Because all case study metadata lives in structured Markdown front matter rather than hardcoded HTML, Hugo templates automatically render the cards, metrics and interactive drawer views consistently. Adding or updating a case study is a content update, not a front-end engineering task.

The key was keeping architectural ownership firmly on my side:

  • I defined the structure and constraints before asking for code—specifying exact HTML semantics, responsive breakpoints and how partials should interact.
  • I reviewed and refactored every suggestion so generated snippets fit my existing Hugo architecture rather than introducing one-off hacks.
  • I verified behavior across viewports and edge cases, because a convincing code suggestion is not the same as a tested, production-ready implementation.

AI sped up repetitive boilerplate work, but every structural decision—what belonged in structured data versus templates, how mobile navigation should collapse, and where editorial layouts needed restraint—required human judgment.

A Text-First Approach to Technical Writing

I also made a deliberate design distinction between the two websites.

For the professional Insights section, I chose a restrained editorial layout focused on clear typography, structured headings and readable prose—without mandatory hero images or decorative visuals. Technical writing is easier to scan and maintain when the presentation stays out of the way.

The Architecture & Stack

Rather than relying on a database-backed CMS or a heavy JavaScript framework, I chose a lightweight static stack built for speed, version control and low maintenance:

  • Hugo (Static Site Generator): Enforces a clean separation between Markdown content, structured front matter and reusable HTML templates, with zero database overhead.
  • Vanilla CSS & JavaScript: Custom CSS grid layouts and lightweight vanilla JS for interactive case study drawers—no external UI frameworks or unnecessary dependencies.
  • Git & GitHub: Separate repositories for each site to isolate changes, track history and maintain a single source of truth.
  • VS Code & Ubuntu: After a Windows security update caused Smart App Control to block the local Hugo binary, I migrated my build environment to Ubuntu rather than weakening OS security settings—reinforcing the value of keeping runtime environments cleanly decoupled from application code.

(For full local environment setup and repository structure details, see the README in the project repository.)

Preparing for Release

A site that renders well locally is not automatically ready for production. Before launch, I worked through a structured release checklist covering responsive breakpoints, internal links, accessibility contrast, draft-filtering behavior,etc.

The Takeaway

Building these two websites reinforced how closely technical architecture and product clarity are connected. AI tools can accelerate implementation, and static site generators can simplify hosting—but maintainable software still comes down to clear requirements, thoughtful data modeling and disciplined review.

Good technical architecture does not just make a website easier to build; it turns every future update into a content decision instead of an engineering project.
